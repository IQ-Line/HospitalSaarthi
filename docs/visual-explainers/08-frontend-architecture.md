The web app is a React 19 + Vite SPA. **TanStack Router** owns the URL tree (file-based), **TanStack Query** owns server state, **Zustand** owns everything client-side (session, tenant, permissions, UI prefs). This page walks the real code in `services/web/src`.

> The LLD at `docs/architecture/lld/frontend/01-frontend-structure.md` is a design sketch and has drifted from the implementation in several places (permission model, store persistence, API client shape, `empi` feature). **Where they disagree, this page follows the code** and calls the gap out.

## Routes vs features — the core split

`routes/` defines *where* (URL structure + data prefetch); `features/` defines *what* (query hooks, mutations, components). A route imports from a feature, never the reverse.

```filetree
. services/web/src/
.   app/
.     providers.tsx — QueryClientProvider + Cerbos principal bridge
.   routes/ — TanStack Router, file-based
.     __root.tsx — beforeLoad: ensureAuthSession()
.     login.tsx — public
.     _authenticated.tsx — guard: redirect /login + hydrate principal
.     _authenticated/ — user-management/ configurator/ visitpad/ opd... 
.     routeTree.gen.ts — AUTO-GENERATED by the router Vite plugin
.   features/ — one dir per module (NOT routes)
.     user-management/
.       api/keys.ts — query-key factory
.       api/queries.ts — queryOptions() + useQuery hooks
.       api/mutations.ts — useMutation + cache invalidation
.       components/ — module-specific UI
.     opd-patients/  billing/  pharmacy/  inventory/  abha/  ...
.   stores/ — global Zustand
.     auth.store.ts — session + tokens + roles
.     tenant.store.ts — active tenant / branch
.     permissions.store.ts — capability-key Set
.     ui-prefs.store.ts — theme, sidebar
.   lib/
.     auth-session.ts — cold-start session bootstrap
.     auth-client.ts — better-auth client
.     api-client.ts — fetch wrapper: auth+tenant headers, 401 retry
.     authorization-context.ts — principal fetch + capability hydration
.     query-client.ts  cerbos-client.ts  permissions.ts
.   styles/index.css — Tailwind v4 + Pulse OKLCH tokens
```

```callout tone=warning title="The LLD's example module is `empi` — it does not exist"
The design doc uses `features/empi/` throughout. In code the real feature dirs are `opd-patients`, `user-management`, `billing`, `pharmacy`, `inventory`, `abha`, `visitpad`, etc. Patient intake lives under Registration/OPD, not an `empi` feature.
```

## Where the JWT lives and how a session survives reload

The durable credential is the **better-auth session cookie** (owned by the browser). The access JWT is short-lived (~5 min), held in `useAuthStore.accessToken`, and persisted to **`sessionStorage`** (`hims-auth-session`) only as a warm-start convenience — the cookie is what actually restores a session.

On every load, `routes/__root.tsx` `beforeLoad` calls `ensureAuthSession()` (`lib/auth-session.ts`). On a hard refresh, prod cookie sessions carry **no** refresh token, so it rebuilds straight off the cookie (GH #90):

```diagram title="Cold-start session bootstrap (lib/auth-session.ts)" look=clean
sequenceDiagram
  participant R as __root beforeLoad
  participant AS as ensureAuthSession
  participant BA as authClient (better-auth)
  participant St as useAuthStore
  R->>AS: ensureAuthSession()
  AS->>St: rehydrate (sessionStorage)
  alt refreshToken in store (dev/legacy)
    AS->>AS: refresh access JWT, done
  else prod cookie session
    AS->>BA: getSession()  (cookie only)
    BA-->>AS: user {id, iq_tenant_id}
    AS->>BA: token()  (mint fresh RS256 JWT off cookie)
    BA-->>AS: access_token
    AS->>St: setSession({accessToken, refreshToken:''})
  end
  alt cookie missing / expired
    AS->>St: clearSession()
    Note over R: guard redirects to /login
  end
```

**Attaching the token.** `lib/api-client.ts` reads the token *outside React* and sets the header on every request — plus the tenant headers both backend plugins read:

```code lang=ts file=lib/api-client.ts hl=2,3
const token = useAuthStore.getState().accessToken;
if (token) headers.set('Authorization', `Bearer ${token}`);
// applyTenantHeaders(): sets BOTH iq_tenant_id AND x-tenant-id from useTenantStore
```

**On 401.** `fetchWithAuthRetry` inspects the error body. A `code: "AUTH_INVALID_TOKEN"` triggers exactly one silent refresh + retry; if the refresh fails, the session is cleared and the app redirects to `/login`. A `403 USER_ACCOUNT_DISABLED` force-logs-out immediately.

```diagram title="401 handling in api-client" look=clean
flowchart LR
  A["fetch"] --> B{"resp.ok?"}
  B -->|yes| Z["return"]
  B -->|no| C{"401 AUTH_INVALID_TOKEN?"}
  C -->|no| E["throw ApiError"]
  C -->|yes| D["refreshAccessToken()"]
  D --> F{"got token?"}
  F -->|yes| G["retry once (no 2nd retry)"]
  F -->|no| H["clearSession + /login"]
```

## Zustand vs TanStack Query

**Rule: selectors always.** `useStore(s => s.field)` — a bare `useStore()` re-renders on every change. For multi-field reads use `useShallow`. Actions live inside the store; `devtools` wraps every store.

**Rule: if it came from an API, it belongs in TanStack Query — not Zustand.** Zustand holds only client state that the server session derives or the UI owns.

```data-model title="Global stores — who owns what (services/web/src/stores)"
. auth.store.ts — persist → sessionStorage (hims-auth-session)
.   accessToken string — short-lived RS256 JWT
.   refreshToken string — '' for prod cookie sessions
.   sessionToken string — better-auth, for sign-out
.   roles string[] — from JWT `roles` claim, UX-only
.   isAuthenticated bool
. tenant.store.ts — persist (noop storage in prod)
.   tenantId string — active working tenant (header)
.   activeBranch string
.   branches array
. permissions.store.ts — NOT persisted
.   capabilityKeys Set — runtime capability keys
.   roles string[] — Cerbos role labels
.   scopes string[] — bounded platform authority
. ui-prefs.store.ts — persist → localStorage (hims-ui-prefs)
.   theme light|dark|system
.   sidebarCollapsed bool
```

```callout tone=warning title="Doc-vs-code: persistence & permission shape"
The LLD says "persist only on `ui-prefs`". **Code persists `auth` (sessionStorage) and `tenant` (noop storage in prod) too.** The LLD also models permissions as a nested `module → feature → action` map with `hasModuleAccess`/`hasFeaturePermission`; **the real store is a flat `Set<capabilityKey>` with `hasCapability`/`hasAnyCapability`/`hasAllCapabilities`.**
```

## Permissions in the UI are UX-only

Capabilities load from `GET /auth/principal` — the guard (`_authenticated.tsx`) calls `refreshAuthorizationContext`, which runs `hydrateCapabilitiesFromPrincipal` (`lib/permissions.ts`) → `usePermissionsStore.setCapabilityKeys(keys, roles, scopes)`. No client-side permission map is fetched from Cerbos.

```diagram title="How capabilities reach the UI" look=clean
flowchart LR
  L["login / route guard"] --> P["GET /auth/principal"]
  P --> H["hydrateCapabilitiesFromPrincipal"]
  H --> S["permissions.store: capabilityKeys Set"]
  S --> G["CapabilityGate / useCapability"]
  G --> U["show/hide UI"]
```

`components/capability-gate.tsx` is the declarative gate; it composes `useCapability` / `useAnyCapability` / `useAllCapabilities`, which are thin selector hooks over the store.

```code lang=tsx file=components/capability-gate.tsx
// UX-only gate. PDP / APIs remain authoritative.
<CapabilityGate capability="users:users:create">
  <NewUserButton />
</CapabilityGate>
// also: <CapabilityGate any={[...]} /> or all={[...]} with optional fallback
```

```callout tone=risk title="Frontend authz is a UX optimization, not a security boundary"
A stale capability Set may show a button the backend rejects. The backend Cerbos PDP re-checks every write — that rejection is the security boundary; the hide is just polish. The Set is refreshed on login, tenant switch, and branch switch.
```

## The data-fetching pattern (worked: user-management)

Three files per feature `api/` dir. Keys are a **factory** so invalidation is surgical:

```code lang=ts file=features/user-management/api/keys.ts
export const userManagementKeys = {
  all: ['user-management'] as const,
  users: () => [...userManagementKeys.all, 'users'] as const,
  userList: () => [...userManagementKeys.users(), 'list'] as const,
  userDetail: (id, scope = 'active-tenant') =>
    [...userManagementKeys.users(), 'detail', id, scope] as const,
};
```

`queryOptions()` co-locates key + fetch, reusable in both a route loader (prefetch) and a component (subscribe):

```code lang=ts file=features/user-management/api/queries.ts hl=6
export function userListOptions(tenantScope?, filter?) {
  return queryOptions({
    queryKey: [...userManagementKeys.userList(), tenantScope ?? 'active-tenant', filter?.department ?? null],
    queryFn: () => apiClient<UmUser[]>(url, { method: 'GET' },
      tenantScope ? { tenantIdOverride: tenantScope } : undefined),
    staleTime: UM_USER_LIST_STALE_MS,
  });
}
export function useUserList(...) { return useQuery({ ...userListOptions(scope, filter) }); }
```

A mutation invalidates the list on success — the cache refetches, no manual state juggling:

```code lang=ts file=features/user-management/api/mutations.ts hl=8
export function useCreateUser() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: ({ body, targetTenantId }) =>
      apiClient<UmUser>(`${BASE}/users`, { method: 'POST', body: JSON.stringify(body) },
        targetTenantId ? { tenantIdOverride: targetTenantId } : undefined),
    onSuccess: () => {
      qc.invalidateQueries({ queryKey: userManagementKeys.userList() });
    },
  });
}
```

## Pulse components

`packages/pulse-*` (`pulse-ui`, `pulse-blocks`, `pulse-layouts`, `pulse-patterns`, `pulse-constants`, `pulse-utils`) are UI components lifted from IQSandbox with `react-router-dom` swapped for `@tanstack/react-router` (verified: `pulse-blocks` imports `@tanstack/react-router`).

```callout tone=decision title="Use the components, ignore their app architecture"
IQSandbox was vibe-coded by PMs. Import the `@pulse/*` widgets, but do NOT copy how it structures routing, state, or data flow — this repo's patterns (routes/features split, Zustand + TanStack Query, capability gating) are authoritative.
```
