# Frontend Structure and Developer Guide

> **Purpose:** This document defines the frontend folder structure, state management architecture, routing patterns, permission integration, and developer conventions for the HIMS platform SPA. A developer reading this document should know where every frontend file goes, how state flows, and how to add a new feature module.
>
> **Prerequisites:** [ADR-0018](../../adr/0018-frontend-stack-zustand-tanstack-router.md) (frontend stack decisions), [HLD-04 §12](../../hld/04-authn-authz-flow.md) (frontend authorization), [Repo Structure LLD](../repo-structure/01-monorepo-setup.md) (monorepo layout).

## 2. Folder structure

```
services/web/src/
├── app/
│   ├── providers.tsx              # QueryClientProvider + CerbosProvider + RouterProvider
│   └── layout.tsx                 # AppShell from @pulse/layouts
│
├── routes/                        # TanStack Router file-based routes
│   ├── __root.tsx                 # Root layout: providers, global error boundary
│   ├── login.tsx                  # Public: login page

│   │   ├── configurator/
│   │   └── ...
│   └── routeTree.gen.ts           # Auto-generated by TanStack Router Vite plugin
│
├── features/                      # Feature logic — NOT routes
│   ├── user-management/

│   │   │   ├── keys.ts            # Query key factory
│   │   │   ├── queries.ts         # queryOptions() + useSuspenseQuery hooks
│   │   │   └── mutations.ts       # useMutation hooks
│   │   ├── components/            # Module-specific UI components
│   │   └── store.ts               # Feature-level Zustand store (if needed)
│   ├── empi/
│   │   ├── api/
│   │   ├── components/
│   │   └── store.ts
│   ├── configurator/
│   └── ...
│
├── stores/                        # Global Zustand stores
│   ├── auth.store.ts              # Session, tokens, login/logout actions
│   ├── tenant.store.ts            # tenantId, tenantName, activeBranch
│   ├── permissions.store.ts       # Permission map from PlanResources
│   └── ui-prefs.store.ts          # Theme, sidebar state (with persist middleware)
│
├── hooks/                         # Shared hooks
│   ├── use-media-query.ts
│   ├── use-debounce.ts
│   └── use-keyboard-shortcut.ts
│
├── lib/
│   ├── api-client.ts              # Base HTTP client with auth + tenant headers
│   ├── query-client.ts            # QueryClient configuration
│   ├── cerbos-client.ts           # @cerbos/http client initialization
│   └── permissions.ts             # Helpers: hasModuleAccess(), hasFeaturePermission()
│
└── styles/
    └── index.css                  # Tailwind v4 + Pulse CSS variables (OKLCH tokens)
```

**Key structural principle:** Routes and features are separated. `routes/` defines the URL structure and connects route-level components to data loading. `features/` contains the business logic (query hooks, mutations, stores, components). A route file imports from `features/`, not the other way around.

## 3. State management architecture

### 3.1 Two layers, clean separation

| Layer | Tool | Scope | Examples |
|-------|------|-------|---------|
| **Server state** | TanStack Query | Cache of server data, deduped fetches, background refresh | Patient list, user details, configuration data, lab results |
| **Client state** | Zustand | Application state that does not come from the server | Auth session, tenant context, permission map, UI preferences, feature-level UI flags |

**The rule:** if the data comes from an API call, it belongs in React Query. If it's client-side state (auth tokens, UI preferences, feature-specific flags), it belongs in Zustand. There is no overlap.

### 3.2 Global stores

#### `auth.store.ts`

```typescript
import { create } from 'zustand';
import { devtools } from 'zustand/middleware';

interface AuthState {
  user: AuthUser | null;
  isAuthenticated: boolean;
  login: (credentials: LoginCredentials) => Promise<void>;
  logout: () => Promise<void>;
  setUser: (user: AuthUser) => void;
}

export const useAuthStore = create<AuthState>()(
  devtools(
    (set) => ({
      user: null,
      isAuthenticated: false,
      login: async (credentials) => {
        const session = await authClient.signIn(credentials);
        set({ user: session.user, isAuthenticated: true }, false, 'login');
      },
      logout: async () => {
        await authClient.signOut();
        set({ user: null, isAuthenticated: false }, false, 'logout');
      },
      setUser: (user) => set({ user, isAuthenticated: true }, false, 'setUser'),
    }),
    { name: 'auth' }
  )
);
```

**Outside-React access:** `useAuthStore.getState().user?.accessToken` — used in API interceptors, WebSocket handlers, background token refresh. No React tree required.

#### `permissions.store.ts`

```typescript
import { create } from 'zustand';
import { devtools } from 'zustand/middleware';

type Actions = Record<string, boolean>; // { read: true, write: false, delete: false }
type Features = Record<string, Actions>;
type PermissionMap = Record<string, Features>; // module → features → actions

interface PermissionsState {
  map: PermissionMap;
  isLoaded: boolean;
  loadPermissions: (tenantId: string) => Promise<void>;
  hasModuleAccess: (module: string) => boolean;
  hasFeaturePermission: (module: string, feature: string, action: string) => boolean;
}

export const usePermissionsStore = create<PermissionsState>()(
  devtools(
    (set, get) => ({
      map: {},
      isLoaded: false,
      loadPermissions: async (tenantId) => {
        const map = await fetchPermissionMap(tenantId); // calls BFF → Cerbos PlanResources
        set({ map, isLoaded: true }, false, 'loadPermissions');
      },
      hasModuleAccess: (module) => {
        const features = get().map[module];
        if (!features) return false;
        return Object.values(features).some(actions =>
          Object.values(actions).some(v => v)
        );
      },
      hasFeaturePermission: (module, feature, action) => {
        return get().map[module]?.[feature]?.[action] ?? false;
      },
    }),
    { name: 'permissions' }
  )
);
```

**Usage in components:**
```typescript
const canWriteRegistration = usePermissionsStore(
  s => s.hasFeaturePermission('opd', 'registration', 'write')
);
// Component only re-renders when this specific permission changes
```

#### `ui-prefs.store.ts`

```typescript
import { create } from 'zustand';
import { devtools, persist } from 'zustand/middleware';

interface UIPrefsState {
  theme: 'light' | 'dark' | 'system';
  sidebarCollapsed: boolean;
  setTheme: (theme: UIPrefsState['theme']) => void;
  toggleSidebar: () => void;
}

export const useUIPrefsStore = create<UIPrefsState>()(
  devtools(
    persist(
      (set) => ({
        theme: 'system',
        sidebarCollapsed: false,
        setTheme: (theme) => set({ theme }, false, 'setTheme'),
        toggleSidebar: () => set(s => ({ sidebarCollapsed: !s.sidebarCollapsed }), false, 'toggleSidebar'),
      }),
      { name: 'hims-ui-prefs' } // localStorage key
    ),
    { name: 'ui-prefs' }
  )
);
```

**Only `ui-prefs` uses `persist` middleware.** Auth and tenant state are derived from the server session, not localStorage.

### 3.3 Feature stores

Feature stores are co-located with their feature and lazy-loaded with the route. They are Zustand stores scoped to one feature's UI needs.

```typescript
// features/opd/store.ts
import { create } from 'zustand';
import { devtools } from 'zustand/middleware';

interface OPDState {
  selectedQueueId: string | null;
  vitalsFormDraft: VitalsDraft | null;
  selectQueue: (id: string) => void;
  saveVitalsDraft: (draft: VitalsDraft) => void;
  clearVitalsDraft: () => void;
}

export const useOPDStore = create<OPDState>()(
  devtools(
    (set) => ({
      selectedQueueId: null,
      vitalsFormDraft: null,
      selectQueue: (id) => set({ selectedQueueId: id }, false, 'selectQueue'),
      saveVitalsDraft: (draft) => set({ vitalsFormDraft: draft }, false, 'saveVitalsDraft'),
      clearVitalsDraft: () => set({ vitalsFormDraft: null }, false, 'clearVitalsDraft'),
    }),
    { name: 'opd' }
  )
);
```

**Not every feature needs a store.** If the feature's UI state is fully captured by URL search params (via TanStack Router) and React Query cache, no Zustand store is needed. Create one when the feature has transient client-side state (drafts, selections, modal flags) that doesn't belong in the URL or in server state.

### 3.4 Zustand conventions (enforced in code review)

| Rule | Why |
|------|-----|
| Always use selectors: `useStore(s => s.field)` | Subscribes only to that field. Without a selector, the component re-renders on every store change. |
| Use `useShallow` for multi-value selects | `useStore(useShallow(s => ({ a: s.a, b: s.b })))` — shallow comparison prevents re-renders when the object reference changes but values don't. |
| One store per feature module | Keeps lazy-loading clean. Prevents god-stores. |
| Actions inside the store | Business logic centralized and testable, not scattered in components. |
| `devtools` middleware on every store | Redux DevTools with named actions. Non-negotiable in development. |
| `persist` only on `ui-prefs` | Auth/tenant state comes from the server. Don't persist transient state. |

## 4. Routing with TanStack Router

### 4.1 File-based routing

The Vite plugin (`@tanstack/router-plugin/vite`) auto-generates the route tree from the `routes/` directory. Developers create files, the plugin creates `routeTree.gen.ts`.

**Naming conventions:**
- `index.tsx` — index route for the parent directory
- `$paramName.tsx` — dynamic path parameter (typed)
- `_layoutName/` — layout route (wraps children, no URL segment)
- `_layoutName.tsx` — the layout component

### 4.2 Type-safe search params

```typescript
// routes/_authenticated/empi/patients.tsx
import { createFileRoute } from '@tanstack/react-router';
import { z } from 'zod';
import { patientKeys, patientListOptions } from '@/features/empi/api/queries';

const patientSearchSchema = z.object({
  search: z.string().optional().default(''),
  status: z.enum(['active', 'inactive', 'merged', 'all']).optional().default('all'),
  department: z.string().optional(),
  page: z.number().int().positive().optional().default(1),
  pageSize: z.number().int().positive().optional().default(25),
});

export const Route = createFileRoute('/_authenticated/empi/patients')({
  validateSearch: patientSearchSchema,
  loaderDeps: ({ search }) => search,
  loader: ({ context, deps }) =>
    context.queryClient.ensureQueryData(patientListOptions(deps)),
  component: PatientListPage,
});

function PatientListPage() {
  const search = Route.useSearch(); // Fully typed: { search: string, status: ..., page: number, ... }
  const { data } = useSuspenseQuery(patientListOptions(search));

  return (
    <Link
      to="/empi/patients"
      search={{ ...search, page: search.page + 1 }}  // Type-checked
    >
      Next page
    </Link>
  );
}
```

### 4.3 Auth guard via layout route

```typescript
// routes/_authenticated/_authenticated.tsx
import { createFileRoute, redirect } from '@tanstack/react-router';
import { useAuthStore } from '@/stores/auth.store';

export const Route = createFileRoute('/_authenticated')({
  beforeLoad: () => {
    if (!useAuthStore.getState().isAuthenticated) {
      throw redirect({ to: '/login' });
    }
  },
  component: AuthenticatedLayout,
});

function AuthenticatedLayout() {
  return (
    <AppShell>
      <Outlet />
    </AppShell>
  );
}
```

### 4.4 Route context for dependency injection

```typescript
// routes/__root.tsx
import { createRootRouteWithContext } from '@tanstack/react-router';
import type { QueryClient } from '@tanstack/react-query';

interface RouterContext {
  queryClient: QueryClient;
}

export const Route = createRootRouteWithContext<RouterContext>()({
  component: RootLayout,
});
```

The `queryClient` is available in every route's `loader` and `beforeLoad` via `context.queryClient`. This enables the canonical `ensureQueryData` pattern without importing the client.

## 5. React Query patterns

### 5.1 Query key factory

Every feature module defines a query key factory in `features/<module>/api/keys.ts`:

```typescript
// features/empi/api/keys.ts
export const patientKeys = {
  all: ['patients'] as const,
  lists: () => [...patientKeys.all, 'list'] as const,
  list: (filters: PatientFilters) => [...patientKeys.lists(), filters] as const,
  details: () => [...patientKeys.all, 'detail'] as const,
  detail: (id: string) => [...patientKeys.details(), id] as const,
};
```

**Invalidation is surgical:**
```typescript
// After a mutation, invalidate the list cache
queryClient.invalidateQueries({ queryKey: patientKeys.lists() });
```

### 5.2 Query options pattern

Co-locate query key + query function in a `queryOptions()` call. Used in both route loaders (prefetch) and components (subscribe):

```typescript
// features/empi/api/queries.ts
import { queryOptions, useSuspenseQuery } from '@tanstack/react-query';
import { patientKeys } from './keys';
import { apiClient } from '@/lib/api-client';

export const patientListOptions = (filters: PatientFilters) =>
  queryOptions({
    queryKey: patientKeys.list(filters),
    queryFn: () => apiClient.get('/empi/patients', { params: filters }),
  });

export const patientDetailOptions = (id: string) =>
  queryOptions({
    queryKey: patientKeys.detail(id),
    queryFn: () => apiClient.get(`/empi/patients/${id}`),
  });

// Usage in route loader:
// loader: ({ context, deps }) => context.queryClient.ensureQueryData(patientListOptions(deps))

// Usage in component:
// const { data } = useSuspenseQuery(patientListOptions(filters))
```

### 5.3 Mutations with cache invalidation

```typescript
// features/empi/api/mutations.ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { patientKeys } from './keys';

export function useRegisterPatient() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (input: RegisterPatientInput) =>
      apiClient.post('/empi/patients/register', input),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: patientKeys.lists() });
    },
  });
}
```

## 6. Frontend authorization

### 6.1 Architecture

```
Login/Context Switch
  │
  ▼
BFF calls Cerbos PlanResources → returns permission map
  │
  ▼
usePermissionsStore.loadPermissions() → stores map in Zustand
  │
  ▼
Components read permissions:
  ├── Cached map (fast):    usePermissionsStore(s => s.hasFeaturePermission(...))
  └── Dynamic check (PDP):  useIsAllowed() from @cerbos/react
```

### 6.2 Provider setup

```typescript
// app/providers.tsx
import { CerbosProvider } from '@cerbos/react';
import { HTTP as CerbosHTTP } from '@cerbos/http';

const cerbosClient = new CerbosHTTP(import.meta.env.VITE_CERBOS_URL);

export function Providers({ children }: { children: React.ReactNode }) {
  return (
    <QueryClientProvider client={queryClient}>
      <CerbosProvider value={cerbosClient}>
        {children}
      </CerbosProvider>
    </QueryClientProvider>
  );
}
```

Auth and tenant are Zustand stores — no Provider needed. Only QueryClient and CerbosProvider are React Context (dependency injection, not state).

### 6.3 Navigation gating

```typescript
// Module tabs in sidebar — only show modules the user has access to
const modules = ['opd', 'empi', 'pharmacy', 'lab'] as const;

function SidebarModules() {
  const hasAccess = usePermissionsStore(
    useShallow(s => Object.fromEntries(
      modules.map(m => [m, s.hasModuleAccess(m)])
    ))
  );

  return (
    <nav>
      {modules.filter(m => hasAccess[m]).map(m => (
        <SidebarLink key={m} to={`/${m}`} />
      ))}
    </nav>
  );
}
```

### 6.4 Dynamic resource-level checks

For checks that depend on a specific resource instance (not just module/feature), use `@cerbos/react` hooks:

```typescript
import { useIsAllowed } from '@cerbos/react';

function ApproveLabResultButton({ resultId, labId }: Props) {
  const user = useAuthStore(s => s.user);
  const { data: allowed, isLoading } = useIsAllowed({
    principal: { id: user.id, roles: user.roles, attr: { tenantId: user.tenantId } },
    resource: { kind: 'lab:result', id: resultId, attr: { labId } },
    action: 'approve',
  });

  if (isLoading || !allowed) return null;
  return <Button onClick={handleApprove}>Approve</Button>;
}
```

### 6.5 Principle

**Frontend authorization is a UX optimization, not a security boundary.** The backend always re-checks via Cerbos PDP. If the permission map is stale (e.g., admin revoked a role 30 seconds ago), the frontend may show a button the backend will reject — the backend rejection is the security boundary, the frontend hide is the UX optimization. The permission map is refreshed on login, tenant switch, and branch switch.

## 8. Adding a new frontend feature

1. **Create the route file** in `routes/_authenticated/<module>/`. The TanStack Router Vite plugin auto-generates the route tree.
2. **Create the feature directory** in `features/<module>/` with `api/keys.ts`, `api/queries.ts`, `api/mutations.ts`, and `components/`.
3. **Define query key factory** in `keys.ts`.
4. **Write query options** in `queries.ts` using `queryOptions()`.
5. **Connect the route** — use `validateSearch` for URL filters, `loader` for prefetching, `component` for the page.
6. **Add permission checks** — ensure the module tab is gated by `usePermissionsStore(s => s.hasModuleAccess('module'))`. Gate write actions with `hasFeaturePermission`.
7. **Create a feature store** only if the feature has transient client-side state that doesn't belong in the URL or server cache.

## 9. API client

```typescript
// lib/api-client.ts
import { useAuthStore } from '@/stores/auth.store';
import { useTenantStore } from '@/stores/tenant.store';

const BASE_URL = import.meta.env.VITE_API_BASE_URL;

export const apiClient = {
  async get<T>(path: string, opts?: { params?: Record<string, unknown> }): Promise<T> {
    const url = new URL(path, BASE_URL);
    if (opts?.params) {
      Object.entries(opts.params).forEach(([k, v]) => {
        if (v !== undefined) url.searchParams.set(k, String(v));
      });
    }
    const res = await fetch(url, { headers: getHeaders() });
    if (!res.ok) throw new ApiError(res);
    return res.json();
  },

  async post<T>(path: string, body: unknown): Promise<T> {
    const res = await fetch(new URL(path, BASE_URL), {
      method: 'POST',
      headers: { ...getHeaders(), 'Content-Type': 'application/json' },
      body: JSON.stringify(body),
    });
    if (!res.ok) throw new ApiError(res);
    return res.json();
  },
};

function getHeaders(): Record<string, string> {
  const headers: Record<string, string> = {};
  const token = useAuthStore.getState().user?.accessToken;
  if (token) headers['Authorization'] = `Bearer ${token}`;
  const tenantId = useTenantStore.getState().tenantId;
  if (tenantId) headers['x-tenant-id'] = tenantId;
  return headers;
}
```

`useAuthStore.getState()` and `useTenantStore.getState()` are called outside React — this is Zustand's killer feature for API infrastructure. No React context threading needed.
