**Key structural principle:** Routes and features are separated. `routes/` defines the URL structure and connects route-level components to data loading. `features/` contains the business logic (query hooks, mutations, stores, components). A route file imports from `features/`, not the other way around.

## 3. State management architecture

### 3.1 Two layers, clean separation

| Layer | Tool | Scope | Examples |
|-------|------|-------|---------|
| **Server state** | TanStack Query | Cache of server data, deduped fetches, background refresh | Patient list, user details, configuration data, lab results |
| **Client state** | Zustand | Application state that does not come from the server | Auth session/tokens, tenant context, capability-key set, UI preferences, feature-level UI flags |

**The rule:** if the data comes from an API call, it belongs in React Query. If it's client-side state (auth tokens, UI preferences, feature-specific flags), it belongs in Zustand. There is no overlap.

### 3.2 Global stores

#### `auth.store.ts`

The store holds the session tokens and identity; it does **not** own login/logout side effects. Sign-in/sign-out flows live in `lib/auth-session.ts` (see §4.5) and call `setSession` / `clearSession`. The store is a persisted state container, not an action hub.

```typescript
// stores/auth.store.ts
interface AuthState {
  isAuthenticated: boolean;
  accessToken: string | null;
  /** Platform refresh token (7d) — mints new access JWTs without a better-auth getSession. */
  refreshToken: string | null;
  /** better-auth session token — used for sign-out. */
  sessionToken: string | null;
  userId: string | null;
  displayName: string | null;
  /** Canonical role codes from the access JWT (`roles` claim), for UX-only shell behaviour. */
  roles: string[];
  /** `null` = not yet checked (session restore); avoids refetching /auth/me on every preload. */
  mustChangePassword: boolean | null;

  setSession: (session: {
    accessToken: string;
    refreshToken: string;
    sessionToken: string;
    userId: string;
    displayName: string;
    mustChangePassword?: boolean | null;
  }) => void;
  setMustChangePassword: (mustChangePassword: boolean | null) => void;
  clearSession: () => void;
}
```

`setSession` derives `roles` from the access token and clears the permission set when the `userId` changes; `clearSession` also clears permissions. The store is wrapped in `persist` (see below), so tokens survive a reload.

**Persistence:** `persist` with `sessionStorage`, key `hims-auth-session`. A `partialize` whitelists what is stored (`accessToken`, `refreshToken`, `sessionToken`, `userId`, `displayName`, `roles`, `isAuthenticated`); `merge`/`onRehydrateStorage` re-derive `roles` from the persisted access token.

**Outside-React access:** `useAuthStore.getState().accessToken` — read in `lib/api-client.ts` to set the `Authorization` header, and in the token-refresh path. No React tree required.

#### `permissions.store.ts`

**Not** a nested `module → feature → action` map. The shell holds a **flat set of capability keys** hydrated from `GET /auth/principal` (`attributes.capabilities` + `attributes.delegated_capabilities`), plus the principal's Cerbos `roles` and bounded platform `scopes`. Membership tests are simple `Set.has` lookups against normalized (trim + lowercase) keys. This mirrors the backend's materialized capability model — the frontend never computes or caches a Cerbos `PlanResources` result.

```typescript
// stores/permissions.store.ts
export type CapabilityKey = string;

export interface PermissionsState {
  capabilityKeys: ReadonlySet<CapabilityKey>;
  /** Cerbos role codes from GET /auth/principal (display label only). */
  roles: readonly string[];
  /** Bounded platform authority scopes from principal.attributes.scopes (e.g. `platform`). */
  scopes: readonly string[];
  isLoaded: boolean;

  setCapabilityKeys: (
    keys: readonly CapabilityKey[],
    roles?: readonly string[],
    scopes?: readonly string[],
  ) => void;
  clearPermissions: () => void;
  hasCapability: (capabilityKey: CapabilityKey) => boolean;
  hasAnyCapability: (capabilityKeys: readonly CapabilityKey[]) => boolean;
  hasAllCapabilities: (capabilityKeys: readonly CapabilityKey[]) => boolean;
}
```

The store is **not** persisted — capabilities are re-hydrated on every login, tenant switch, and cold-start restore (see §4.5, §6). Hydration is done by `hydrateCapabilitiesFromPrincipal()` in `lib/permissions.ts`:

```typescript
// lib/permissions.ts
export async function hydrateCapabilitiesFromPrincipal(
  principal?: AuthPrincipalResponse,
): Promise<void> {
  const payload = principal ?? (await fetchAuthPrincipal()); // GET /auth/principal
  const keys = capabilityKeysFromPrincipalAttributes(payload.attributes);
  const scopes = extractStringArray(payload.attributes?.scopes);
  usePermissionsStore.getState().setCapabilityKeys(keys, payload.roles, scopes);
}
```

**Usage in components:**
```typescript
const canManageUsers = usePermissionsStore(s => s.hasCapability('user-management:users:write'));
// Component only re-renders when this specific capability changes.
// Multi-capability gates: hasAnyCapability([...]) / hasAllCapabilities([...]).
```

#### `ui-prefs.store.ts`

```typescript
import { create } from 'zustand';
import { devtools, persist } from 'zustand/middleware';

interface UIPrefsState {
  theme: 'light' | 'dark' | 'system';
  sidebarCollapsed: boolean;
  setTheme: (theme: UIPrefsState['theme']) => void;
  toggleSidebar: () => void;
}

export const useUIPrefsStore = create<UIPrefsState>()(
  devtools(
    persist(
      (set) => ({
        theme: 'system',
        sidebarCollapsed: false,
        setTheme: (theme) => set({ theme }, false, 'setTheme'),
        toggleSidebar: () => set(s => ({ sidebarCollapsed: !s.sidebarCollapsed }), false, 'toggleSidebar'),
      }),
      { name: 'hims-ui-prefs' } // localStorage key
    ),
    { name: 'ui-prefs' }
  )
);
```

**Three stores use `persist`, each for a different reason:** `ui-prefs` (localStorage — durable user preferences), `auth` (sessionStorage `hims-auth-session` — survives a reload/hard-refresh within the tab; see §4.5), and `tenant` (sessionStorage in dev only, a no-op storage in prod — dev convenience, no cross-session tenant leakage). `permissions` is **never** persisted — it is re-hydrated from `/auth/principal` on every session restore and context switch.

### 3.3 Feature stores

Feature stores are co-located with their feature and lazy-loaded with the route. They are Zustand stores scoped to one feature's UI needs.

Real examples: `features/create-rx/create-rx.store.ts`, `features/frontdesk/visit-registration-sections.store.ts`. The pattern:

```typescript
// features/<module>/<name>.store.ts
import { create } from 'zustand';
import { devtools } from 'zustand/middleware';

interface DraftState {
  selectedId: string | null;
  formDraft: Draft | null;
  select: (id: string) => void;
  saveDraft: (draft: Draft) => void;
  clearDraft: () => void;
}

export const useDraftStore = create<DraftState>()(
  devtools(
    (set) => ({
      selectedId: null,
      formDraft: null,
      select: (id) => set({ selectedId: id }, false, 'select'),
      saveDraft: (draft) => set({ formDraft: draft }, false, 'saveDraft'),
      clearDraft: () => set({ formDraft: null }, false, 'clearDraft'),
    }),
    { name: 'draft' }
  )
);
```

**Not every feature needs a store.** If the feature's UI state is fully captured by URL search params (via TanStack Router) and React Query cache, no Zustand store is needed. Create one when the feature has transient client-side state (drafts, selections, modal flags) that doesn't belong in the URL or in server state.

### 3.4 Zustand conventions (enforced in code review)

| Rule | Why |
|------|-----|
| Always use selectors: `useStore(s => s.field)` | Subscribes only to that field. Without a selector, the component re-renders on every store change. |
| Use `useShallow` for multi-value selects | `useStore(useShallow(s => ({ a: s.a, b: s.b })))` — shallow comparison prevents re-renders when the object reference changes but values don't. |
| One store per feature module | Keeps lazy-loading clean. Prevents god-stores. |
| Actions inside the store | Business logic centralized and testable, not scattered in components. |
| `devtools` middleware on every store | Redux DevTools with named actions. Non-negotiable in development. |
| `persist` deliberately, with `partialize` | `ui-prefs` (localStorage), `auth` + `tenant` (sessionStorage; tenant is dev-only). Never persist `permissions` — it re-hydrates from `/auth/principal`. Whitelist persisted fields with `partialize`. |

## 4. Routing with TanStack Router

### 4.1 File-based routing

The Vite plugin (`@tanstack/router-plugin/vite`) auto-generates the route tree from the `routes/` directory. Developers create files, the plugin creates `routeTree.gen.ts`.

**Naming conventions:**
- `index.tsx` — index route for the parent directory
- `$paramName.tsx` — dynamic path parameter (typed)
- `_layoutName/` — layout route (wraps children, no URL segment)
- `_layoutName.tsx` — the layout component

### 4.2 Type-safe search params

```typescript
// routes/_authenticated/user-management.tsx (illustrative shape)
import { createFileRoute } from '@tanstack/react-router';
import { z } from 'zod';
import { userListOptions } from '@/features/user-management/api/queries';

const userSearchSchema = z.object({
  department: z.string().optional(),
});

export const Route = createFileRoute('/_authenticated/user-management')({
  validateSearch: userSearchSchema,
  loaderDeps: ({ search }) => search,
  loader: ({ context, deps }) =>
    context.queryClient.ensureQueryData(userListOptions(null, { department: deps.department })),
  component: UserListPage,
});

function UserListPage() {
  const search = Route.useSearch(); // Fully typed: { department?: string }
  const { data } = useSuspenseQuery(userListOptions(null, { department: search.department }));
  // ...
}
```

### 4.3 Auth guard via layout route

The guard is a **sibling file** `routes/_authenticated.tsx` (not `_authenticated/_authenticated.tsx`), and its `beforeLoad` is `async` — it does three things: reject unauthenticated users, hydrate shell authorization for the active scope, and enforce a pending password change. It does **not** wrap children in a `@pulse` `AppShell`; the shell (sidebar + header) is composed inline from `components/layout/*`.

```typescript
// routes/_authenticated.tsx
export const Route = createFileRoute('/_authenticated')({
  beforeLoad: async ({ context, location }) => {
    const { isAuthenticated } = useAuthStore.getState();
    if (!isAuthenticated) {
      throw redirect({ to: '/login' });
    }
    // Loads GET /auth/principal and hydrates capability keys for {userId, tenantId, activeBranch}.
    await refreshAuthorizationContext(context.queryClient);
    // Redirects to /change-password when the principal must rotate their password
    // (checks the store, else falls back to GET /auth/me).
    await enforcePasswordChange(location.pathname);
  },
  component: AuthenticatedLayout,
});

function AuthenticatedLayout() {
  // Shows a "Loading capabilities..." gate until usePermissionsStore.isLoaded,
  // then renders <AppSidebar/> + <AppHeader/> + <Outlet/>. A useEffect re-hydrates
  // capabilities when {userId, tenantId, activeBranch} changes, with a bounded
  // retry when the principal returns an empty capability set.
  // ...
}
```

Capability hydration is therefore driven by the route lifecycle, not by a store action a component calls. `refreshAuthorizationContext` (`lib/authorization-context.ts`) is the single entry point; it dedupes by scope, reuses the React Query principal cache when the scope is unchanged, and clears permissions when the scope is incomplete.

### 4.4 Route context for dependency injection

```typescript
// routes/__root.tsx
import { createRootRouteWithContext } from '@tanstack/react-router';
import type { QueryClient } from '@tanstack/react-query';
import { ensureAuthSession } from '@/lib/auth-session';

export interface RouterContext {
  queryClient: QueryClient;
}

export const Route = createRootRouteWithContext<RouterContext>()({
  // Runs once before the tree loads: restore/repair the session (see §4.5).
  beforeLoad: async () => {
    await ensureAuthSession();
  },
  component: RootComponent, // <Outlet/> + <Toaster/>
});
```

The `queryClient` is available in every route's `loader` and `beforeLoad` via `context.queryClient`. This enables the canonical `ensureQueryData` pattern without importing the client.

### 4.5 Session bootstrap and cookie restore

Before any authenticated route can run its guard, the session in memory must be restored on a cold start (hard refresh, new tab). `ensureAuthSession()` in `lib/auth-session.ts` is called once from the root `beforeLoad` and is idempotent (a module-level promise dedupes concurrent callers). It runs three branches in order:

1. **Rehydrate the persisted auth store**, then bail out on `/login` (that page owns `POST /auth/login`).
2. **Refresh-token-backed session** (dev / legacy POST-login): if a `refreshToken` is present and the access token is still usable, hydrate tenant context and return; otherwise mint a fresh access JWT via `GET /api/auth/token`.
3. **Cookie bootstrap** (prod, GH #90): prod cookie sessions carry **no** refresh token (`refreshToken === ''`), so a hard refresh has nothing in memory to restore. Instead the session is rebuilt straight off the better-auth cookie, mirroring login exactly:

```typescript
// lib/auth-session.ts — bootstrapSessionFromCookie()
const sessionResult = await authClient.getSession(); // cookie-only → platform identity
// ... userId from sessionResult.data.user.id ...
const tokenResult = await authClient.token();        // fresh RS256 access JWT off the same cookie

useAuthStore.getState().setSession({
  accessToken,
  refreshToken: '',   // cookie sessions issue no refresh token; the cookie is the durable credential
  sessionToken: sessionData?.session?.token ?? '',
  userId,
  displayName: user?.name ?? '',
});
await applyTenantSessionFromAuth({ accessToken, authUserIqTenantId: user?.iq_tenant_id ?? null });
```

A missing/expired cookie makes `getSession()`/`token()` return an error or empty body; the bootstrap returns `false`, the session is cleared, and the router falls through to the `/login` redirect. **No new access token or principal is written to web storage** — the cookie is the only durable credential and it is owned by the browser. Capability hydration then runs as usual via the `_authenticated` guard's `refreshAuthorizationContext` (§4.3).

## 5. React Query patterns

### 5.1 Query key factory

Every feature module defines a query key factory in `features/<module>/api/keys.ts`:

```typescript
// features/user-management/api/keys.ts
export const userManagementKeys = {
  all: ['user-management'] as const,
  users: () => [...userManagementKeys.all, 'users'] as const,
  userList: () => [...userManagementKeys.users(), 'list'] as const,
  userDetail: (id: string, tenantScopeKey = 'active-tenant') =>
    [...userManagementKeys.users(), 'detail', id, tenantScopeKey] as const,
  roles: () => [...userManagementKeys.all, 'roles'] as const,
  roleList: () => [...userManagementKeys.roles(), 'list'] as const,
};
```

**Invalidation is surgical:**
```typescript
// After a mutation, invalidate the list cache
queryClient.invalidateQueries({ queryKey: userManagementKeys.userList() });
```

### 5.2 Query options pattern

Co-locate query key + query function in a `queryOptions()` call. Used in both route loaders (prefetch) and components (subscribe):

Note the API client is a generic **function** `apiClient<T>(path, options, context)` — not an object with `.get()`/`.post()`. The HTTP method goes in `options.method`; the response type is the type argument (see §9).

```typescript
// features/user-management/api/queries.ts
import { queryOptions } from '@tanstack/react-query';
import { apiClient } from '@/lib/api-client';
import { userManagementKeys } from './keys';
import type { UmUser } from '../types';

const BASE = '/api/user-management';

export function userListOptions(tenantScope?: string | null, filter?: { department?: string }) {
  const qs = filter?.department ? `?department=${encodeURIComponent(filter.department)}` : '';
  return queryOptions({
    queryKey: [...userManagementKeys.userList(), tenantScope ?? 'active-tenant', filter?.department ?? null] as const,
    queryFn: () =>
      apiClient<UmUser[]>(
        `${BASE}/users${qs}`,
        { method: 'GET' },
        tenantScope ? { tenantIdOverride: tenantScope } : undefined, // cross-tenant super-admin reads
      ),
    staleTime: 60_000,
  });
}

// Usage in route loader:
// loader: ({ context, deps }) => context.queryClient.ensureQueryData(userListOptions(null, deps))
// Usage in component:
// const { data } = useSuspenseQuery(userListOptions(null, filter))
```

### 5.3 Mutations with cache invalidation

```typescript
// features/user-management/api/mutations.ts
import { useMutation, useQueryClient } from '@tanstack/react-query';
import { apiClient } from '@/lib/api-client';
import { userManagementKeys } from './keys';

export function useCreateUser() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: (input: CreateUserInput) =>
      apiClient<UmUser>('/api/user-management/users', { method: 'POST', body: JSON.stringify(input) }),
    onSuccess: () => {
      queryClient.invalidateQueries({ queryKey: userManagementKeys.userList() });
    },
  });
}
```

Mutation errors surface automatically as toasts — the shared `QueryClient` (`lib/query-client.ts`) installs a `MutationCache.onError` that formats `ApiError` bodies via `sonner`.

## 6. Frontend authorization

### 6.1 Architecture

The frontend does **not** call Cerbos `PlanResources` and does not build a permission map client-side. Shell gating reads a flat capability-key set hydrated from `GET /auth/principal`. The `@cerbos/http` client exists only as a UX-only bridge for the occasional resource-level `useIsAllowed` check (§6.4).

```
Login / Tenant switch / Cold-start restore
  │
  ▼
refreshAuthorizationContext(queryClient)   (lib/authorization-context.ts)
  │  fetchAuthPrincipal() → GET /auth/principal  { id, roles, attributes }
  ▼
hydrateCapabilitiesFromPrincipal()  →  usePermissionsStore.setCapabilityKeys(keys, roles, scopes)
  │
  ▼
Components read permissions:
  ├── Capability set (fast):   usePermissionsStore(s => s.hasCapability('module:feature:action'))
  └── Resource-level (rare):   useIsAllowed() from @cerbos/react — UX-only bridge, PDP authoritative
```

### 6.2 Provider setup

```typescript
// app/providers.tsx
export function AppProviders({ children }: { children: ReactNode }): ReactElement {
  return (
    <QueryClientProvider client={queryClient}>
      <CerbosPrincipalBridge>{children}</CerbosPrincipalBridge>
    </QueryClientProvider>
  );
}
```

`CerbosPrincipalBridge` reads the cached `/auth/principal` from React Query (`enabled: false` — it never fetches; `refreshAuthorizationContext` is the sole network writer), maps it to a Cerbos `Principal`, and supplies it — plus an optional `auxData.jwt` when the access token looks like a JWT — to `<CerbosProvider client={cerbosClient} …>`. When the principal is not yet loaded it uses a no-grant placeholder (`roles: ['_unresolved']`), and an anonymous principal when signed out.

Auth, tenant, and the capability set are Zustand stores — **no Provider** needed. Only `QueryClient` and the Cerbos client are React Context (dependency injection, not state). The Cerbos hooks are UX-only; APIs and the PDP remain authoritative.

### 6.3 Navigation gating

```typescript
// Nav items — gate each on a capability key. Use useShallow for multi-key reads.
function SidebarModules() {
  const canSee = usePermissionsStore(
    useShallow(s => ({
      users: s.hasCapability('user-management:users:read'),
      billing: s.hasCapability('billing:invoices:read'),
      pharmacy: s.hasAnyCapability(['pharmacy:dispense:read', 'pharmacy:stock:read']),
    }))
  );

  return (
    <nav>
      {canSee.users && <SidebarLink to="/user-management" />}
      {canSee.billing && <SidebarLink to="/billing-and-finance" />}
      {canSee.pharmacy && <SidebarLink to="/pharmacy" />}
    </nav>
  );
}
```

### 6.4 Dynamic resource-level checks

For checks that depend on a specific resource instance (not just a capability key), use `@cerbos/react` hooks. The principal is supplied by `CerbosPrincipalBridge` (§6.2), so the hook needs only the resource and action — this is a **UX-only** convenience, not a security boundary:

```typescript
import { useIsAllowed } from '@cerbos/react';

function ApproveButton({ resourceId, attr }: Props) {
  const { data: allowed, isLoading } = useIsAllowed({
    resource: { kind: 'lab:result', id: resourceId, attr },
    action: 'approve',
  });

  if (isLoading || !allowed) return null;
  return <Button onClick={handleApprove}>Approve</Button>;
}
```

### 6.5 Principle

**Frontend authorization is a UX optimization, not a security boundary.** The backend always re-checks via the Cerbos PDP. If the capability set is stale (e.g., an admin revoked a role 30 seconds ago), the frontend may show a control the backend will reject — the backend rejection is the security boundary, the frontend hide is the UX optimization. The capability set is re-hydrated from `/auth/principal` on login, tenant switch, and branch switch (any change to `{userId, tenantId, activeBranch}`), and on cold-start restore.

## 8. Adding a new frontend feature

1. **Create the route file** in `routes/_authenticated/<module>/`. The TanStack Router Vite plugin auto-generates the route tree.
2. **Create the feature directory** in `features/<module>/` with `api/keys.ts`, `api/queries.ts`, `api/mutations.ts`, and `components/`.
3. **Define query key factory** in `keys.ts`.
4. **Write query options** in `queries.ts` using `queryOptions()`.
5. **Connect the route** — use `validateSearch` for URL filters, `loader` for prefetching, `component` for the page.
6. **Add permission checks** — gate the nav item and write actions on capability keys: `usePermissionsStore(s => s.hasCapability('module:feature:action'))` (or `hasAnyCapability` / `hasAllCapabilities`).
7. **Create a feature store** only if the feature has transient client-side state that doesn't belong in the URL or server cache.

## 9. API client

The client is a generic **function**, `apiClient<T>(path, options?, context?)`, not an object with `.get()`/`.post()`. The HTTP method lives in `options.method`; the return type is the type argument. It reads the token and tenant from Zustand outside React, attaches auth + tenant headers, and transparently retries once on an expired access token.

```typescript
// lib/api-client.ts
export async function apiClient<T>(
  path: string,
  options: RequestInit = {},
  context?: ApiClientContext,   // { tenantIdOverride?: string | null } — override/omit tenant scope
): Promise<T> {
  return parseJsonResponse<T>(await fetchWithAuthRetry(path, options, context, true));
}

export class ApiError extends Error {
  constructor(public readonly status: number, public readonly body: string) {
    super(`API error ${status}: ${body}`);
    this.name = 'ApiError';
  }
}
```

What `apiClient` does beyond a bare `fetch`:

- **Auth header** — `Authorization: Bearer <accessToken>` read from `useAuthStore.getState().accessToken` (outside React). For OPD writes it also derives `x-user-id` from the JWT `sub` when the gateway does not inject it.
- **Tenant headers** — sets **both** `iq_tenant_id` **and** `x-tenant-id` (different backend tenant plugins read different names). The active tenant comes from `useTenantStore`; `context.tenantIdOverride` can pin a cross-tenant super-admin scope or (`null`) omit tenant headers entirely for global-catalog reads. Per-service normalization (`normalizeServiceTenantHeaders`) applies billing/EMPI/registration/configurator quirks, and a guard blocks a visitpad catalog write that would silently fall through to the `global_master` library.
- **401 refresh-retry** — on a `401` with body code `AUTH_INVALID_TOKEN`, it calls `refreshAccessToken()` (§4.5) and retries the request **once** with the fresh token. A `403` `USER_ACCOUNT_DISABLED` forces logout. `credentials: 'include'` is always sent so the better-auth cookie rides along.
- **Response parsing** — `204`/empty bodies return `undefined`; non-OK responses throw `ApiError(status, body)`, which `query-client.ts` formats into toasts.

Sibling exports share the same auth/tenant/retry pipeline for non-JSON payloads: `apiClientFormData` (multipart upload), `apiClientBlob` (e.g. PDF), `apiClientText` (HTML/text), `apiClientWithIqTenant` / `apiClientGlobalCatalogRead` (explicit tenant scoping).

`useAuthStore.getState()` and `useTenantStore.getState()` are called outside React — this is Zustand's killer feature for API infrastructure. No React context threading needed.
