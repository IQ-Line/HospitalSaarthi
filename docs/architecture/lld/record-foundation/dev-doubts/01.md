# Record Foundation -- LLD-deferred implementation doubts

These are the implementation-stage choices the LLD intentionally does not lock in.

---

### 1. Bundle digital signatures

Should v1 sign every finalised bundle?

**Recommendation:** No. The schema accommodates signatures (`signature_storage_ref` column on `record_bundle_manifests`) so signing can be enabled later without migration. v1 leaves the column NULL. Signing requires per-tenant signing-key provisioning, which is its own LLD when needed (likely Phase 2 once compliance team raises it).

---

### 2. Validation strictness policy

Internal vs external bundle validation policies differ:

| Producer | Policy |
|---|---|
| `producer_kind = 'platform_module'` | **Reject on validation failure.** A bug in our serialiser must not leak to the vault. The `consultation.finalized` event is dead-lettered; ops alerted. |
| `producer_kind = 'external_hip'` | **Warn-and-store.** We cannot reject what an external HIP has already sent. Store with `validation_status='invalid'` and surface warnings on the record viewer. |

This policy is in `01-schema-design.md` but worth restating as the implementation rule.

---

### 3. Object-storage extraction threshold

When does a bundle move from `bundle_storage.bundle_jsonb` to object storage?

**Recommendation:** 256 KiB. Below that, JSONB inline is fine. Above (typical for Discharge Summaries with attached PDF/images), object-storage extraction. v1 ships with 100% inline; the threshold is a runtime config. The migration job (post-launch) walks rows >256KB and moves them.

---

### 4. Timeline projection rebuild strategy

The `timeline_index` is rebuildable. How is the rebuild triggered?

**Recommendation:** Event-driven incremental as the default; nightly full rebuild as a safety-net (cron at 03:00 IST). Manual rebuild via `POST /api/v1/admin/timeline/rebuild?patient_id=X` for one-off corrections. The nightly full rebuild detects projection drift; if it finds rows differing from the source-truth-replay, it reports the deltas via metric and overwrites.

---

### 5. Erasure scheduler cadence

Nightly is the default. Is hourly closer to "as soon as `data_erase_at` passes"?

**Recommendation:** Nightly v1. Hourly is unnecessary precision -- DPDP and ABDM tolerate end-of-day erasure. Hourly multiplies log noise without benefit. Manual erasure (`POST /api/v1/admin/erasure-runs`) is available for incident response.

---

### 6. Care-context display strings

`care_contexts.display` is patient-facing. Does Record Foundation generate it, or do source modules pass it in their finalised event?

**Recommendation:** Source modules pass display in the event payload. They know the domain ("Cardiology OPD visit -- Dr Verma -- 12 Mar 2026"). Record Foundation stores verbatim. If a tenant wants different formatting, that is a source-module concern.

---

### 7. External record `display_summary` parsing

How much do we extract from a received external bundle into the structured `display_summary`?

**Recommendation:** Only what the timeline row needs: `title` (from `Composition.title`), `attestor` (`Composition.attester[0].party.display`), `encounterDate` (`Composition.date`), `primaryDiagnosis` (first `Condition` in the first Section). Anything more is read from the bundle bytes when the doctor opens the record.

---

### 8. Phase 4 EMR product API

The eventual EMR product needs a stable API. Should v1 already expose the public-facing endpoints?

**Recommendation:** v1 exposes the endpoints listed in the OpenAPI spec; v2 will add the richer Phase 4 ones (specialty filters, AI summaries, deficiency workflows). v1 endpoints are forward-compatible -- new optional query params are additive.

---

### 9. Bundle storage strategy: `inline_jsonb` only for v1

The schema supports `storage_kind` enumeration; v1 hard-codes `inline_jsonb`.

**Recommendation:** Yes. Object-storage path in v2 once a real bundle exceeds the threshold (#3). The `storage_kind` column is the seam.

---

### 10. Care-context superseded chain depth

If a record is amended N times, the chain `original -> amended -> amended -> ...` could be long. Limits?

**Recommendation:** No artificial limit. The chain is sparse (most records never amend). Display shows "amended N times" and lets the user expand history.

---

### 11. Encrypted-at-rest policy

`bundle_storage.encryption_kind = 'at_rest_pg'` relies on PostgreSQL's at-rest encryption (deployment-platform-provided).

**Recommendation:** Sufficient for v1. Application-level envelope encryption (`encryption_kind='app_encrypted'`) is a separate ADR (deferred) and adds key-management complexity.

---

### 12. Timeline-disclosable-flag race

Between `abdm.consent.granted` (sets `consent_disclosable=true`) and a HIP discovery query, there is a brief window. Is read-after-write consistency sufficient?

**Recommendation:** Yes. Both consumer and discovery query are within the Record Foundation service. The event-driven projection update is in the same shard as the discovery query; PostgreSQL's read-your-writes within a session is enough. Cross-shard concerns do not arise (everything is per-tenant).
