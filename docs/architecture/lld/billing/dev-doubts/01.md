# Billing — dev-doubts 01

Implementation choices that the LLD intentionally leaves to the developer, with recommendations and the reasoning behind them. None of these block the schema, but each will need a decision before the first commit lands.

---

## Bill / payment / receipt number format

**Choice (Phase 1):** how to generate human-readable, tenant-unique sequence numbers on `bills.bill_number`, `payments.payment_number`, `payments.receipt_number`. (`patient_advances.advance_number` lands in Phase 2 alongside the advances table; same scheme applies.)

**Recommendation:** prefix + date + sequence, generated by a tenant-scoped Postgres sequence backed by a `tenant_number_sequences` table.

- Format: `B-<TENANT_SHORT>-<YYYYMMDD>-<SEQ6>` for bills (e.g., `B-AIIMS-D-20260513-000001`).
  - `R-...` for receipts, `P-...` for payments (the internal payment number; receipt number is what the patient sees). `A-...` for advances (Phase 2).
- `tenant_number_sequences (iq_tenant_id, kind, date, last_seq)`. UPSERT on conflict + return new seq. One row per tenant per kind per day.
- Reset daily simplifies operator mental model and matches production HIMS practice.

**Why not just `uuid`s as the public number?** Operators read these aloud over phones. UUIDs are hostile to that workflow.

**Why not a global Postgres `SEQUENCE`?** Citus has known issues with shared sequences across shards; a per-tenant table-backed sequence is shard-local and correct.

**Why not Snowflake-style IDs?** Overkill for ~10⁵ bills per tenant per year.

## Money type — `NUMERIC(18,4)` vs paise-as-bigint

**Choice:** how to represent currency amounts in the DB and in the application layer.

**Recommendation:** `NUMERIC(18,4)` in the DB, application-layer `Money` value object that wraps `string` (avoid JS float coercion) and rounds explicitly at the display boundary.

- `NUMERIC` is more legible in SQL and supports four-decimal tax math without rounding loss.
- The `Money` value object enforces invariants (non-negative for amounts, positive for prices) and provides `add`, `subtract`, `multiply(quantity)`, `applyTax(rate)`, `round(2)`.
- Use a library like `dinero.js` (TypeScript) or roll a small wrapper; do **not** use raw JavaScript `number` for money — IEEE 754 floats silently break sums.

**Why not paise-as-bigint?**

- Pros: integer arithmetic is bit-exact, faster, fewer surprises.
- Cons: every read needs a `/100` for display; tax math at four decimals (CGST 9% on ₹103.27) overflows the integer paise abstraction unless we go to centipaise or finer, which defeats the legibility argument.
- Verdict: `NUMERIC(18,4)` wins for legibility and tax math; the `Money` wrapper hides JS float issues at the application boundary.

**Decision constraint:** whichever choice is taken, it must be enforced platform-wide via a shared `@hims/ts-sdk-money` package, otherwise modules silently drift. Phase 1 can ship without the SDK if billing is the only module touching money; add the SDK when the second module (Pharmacy stock pricing, etc.) needs it.

## Bill-item immutability enforcement

**Choice:** how to enforce the "bill_items financial fields are immutable once the parent bill is not DRAFT" invariant.

**Recommendation (Phase 1):** application-layer enforcement in the `BillItemRepo.update()` method. The repo reads the parent bill's status before allowing any UPDATE; on non-DRAFT, throws an `InvariantViolationError`.

**Future hardening (Phase 2 or 3):** add a Postgres trigger:

```sql
CREATE OR REPLACE FUNCTION billing.fn_bill_items_immutable_post_draft()
RETURNS TRIGGER AS $$
DECLARE
  parent_status TEXT;
BEGIN
  SELECT status INTO parent_status FROM billing.bills
    WHERE id = NEW.bill_id AND iq_tenant_id = NEW.iq_tenant_id;
  IF parent_status IS DISTINCT FROM 'DRAFT' THEN
    RAISE EXCEPTION 'bill_items rows are immutable once parent bill is %', parent_status
      USING ERRCODE = 'check_violation';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_bill_items_immutable
  BEFORE UPDATE ON billing.bill_items
  FOR EACH ROW EXECUTE FUNCTION billing.fn_bill_items_immutable_post_draft();
```

Phase 1 relies on application enforcement to keep the developer surface small and the dev-loop fast. The trigger is added once the team has a second-mover risk (a script, an admin tool, or a Phase 2 module reaching directly into the table).

## Advance utilisation concurrency  [Phase 2 — NOT in Phase 1]

> **Not a Phase 1 concern.** Advances ship in Phase 2 alongside IPD admission deposits. This entry stays as forward reference for the Phase 2 build.

**Choice:** how to prevent two concurrent counter operators from over-utilising the same advance.

**Recommendation:** `SELECT ... FOR UPDATE` on the `patient_advances` row inside the utilisation transaction, plus the `CHECK (available_balance >= 0)` constraint as the last-line defence.

```typescript
// Pseudo-code in use-cases/utilize-advance.ts
await db.transaction(async (tx) => {
  const advance = await tx
    .select()
    .from(patientAdvances)
    .where(and(eq(patientAdvances.id, advanceId), eq(patientAdvances.iqTenantId, tenantId)))
    .for('update')
    .then(first);
  if (advance.availableBalance < utilizedAmount) {
    throw new InsufficientAdvanceBalance(advance.availableBalance);
  }
  await tx.insert(advanceUtilizations).values({ ... });
  await tx.update(patientAdvances).set({
    utilizedAmount: advance.utilizedAmount + utilizedAmount,
    availableBalance: advance.availableBalance - utilizedAmount,
  }).where(...);
  await tx.update(bills).set({ /* roll-up */ }).where(...);
});
```

**Alternatives considered:**

- **Optimistic locking via version column** — works for low-contention cases but generates retry storms when two operators target the same advance simultaneously. `FOR UPDATE` is the right primitive here because the conflict is real and serialisation is the answer.
- **Postgres advisory locks keyed by `advance_id`** — equivalent to `FOR UPDATE` in effect but harder to reason about. Skip.
- **Application-level mutex** — would only work in single-process Phase 1 deployment; doesn't extend.

## Tax-rate snapshot vs lookup

**Choice:** whether `bill_items.tax_percentage` and `tax_category` snapshot from `service_master` at charge time (current LLD) or look up on each read.

**Recommendation:** snapshot. Already decided in [ADR-0025](../../../adr/0025-billing-module-shape-and-phasing.md). Listed here for completeness because developers will be tempted to "save a column" by reading via join.

**Why this temptation is wrong:**

- GST rates change. A bill issued in March under 12% must remain a 12% bill even after April when the rate moves to 18%.
- A re-print of an old receipt must show the same tax that was charged.
- The catalog row might be reclassified (move from `EXEMPT` to `CGST_SGST`); historical bills are untouched by such reclassification.

**Implementation note:** the snapshot happens in the `capture-charge` use-case, in the same transaction as the `bill_items` INSERT, against the `service_master` row read just before. Reading `service_master` at end-of-day reporting time is fine — that is current state, not historical.

## Soft-delete vs status on cancellation

**Choice:** how to represent a cancelled bill / voided bill_item / voided payment.

**Recommendation:** status enum, not soft-delete column.

- `bills.status = 'CANCELLED'` rather than `bills.is_deleted = true`.
- `bill_items.status = 'VOIDED'` rather than `bill_items.is_deleted = true`.
- `payments.status = 'VOIDED'` likewise.

**Why:**

- A status enum captures *why* the row is no longer active (`CANCELLED` vs `REPLACED` vs `CLOSED`); a boolean does not.
- State-machine reasoning is centralised on one column instead of split across `status` and `is_deleted`.
- Roll-up queries (`SUM(amount) WHERE status='SUCCESS'`) read clearly; soft-delete adds another `AND is_deleted = false` to every query.

**Exception:** `is_active` on `service_master`, `price_agreements`, `insurance_providers` — these are catalog tables, not transactional, and `is_active` is a tenant-managed activation flag, not a soft-delete.

## Receipt PDF generation

**Choice:** how the receipt / invoice PDF is generated.

**Recommendation:** server-side, via a templated PDF service using Puppeteer or Playwright (Chromium-based). HTML template + tenant-scoped CSS + assets.

- A single template per locale per tenant; tenant CSS overrides come from Configurator.
- The PDF service runs as a separate process (`services/pdf-svc`) or as a containerised microservice; billing calls it with a JSON payload of the bill + patient display fields.
- Output is streamed back; no persistent storage in billing.

**Alternatives:**

- **Client-side print** (browser print-to-PDF) — simplest but lacks consistency. Receipts must look identical regardless of operator's browser.
- **PDFKit / wkhtmltopdf** — works but Puppeteer/Playwright handle modern CSS far better; receipt designs are inevitably designer-driven.
- **A SaaS PDF service (DocRaptor, PDFShift)** — fast to start but adds an external dependency for a core flow.

Phase 1 can ship with client-side print as a temporary expedient; server-side PDF service follows shortly after.

## Idempotency-Key TTL and storage

**Choice:** how long the `bill_items.idempotency_key` uniqueness window persists.

**Recommendation:** **30 days**, then a sweep job NULLs the column on bill_items older than 30 days (and the partial unique index allows the row to remain).

- 30 days covers reasonable retry windows for an outbox-driven clinical module.
- Clearing the key after 30 days prevents the column from being a permanent leak of clinical-row IDs into billing's table.
- The clinical module's outbox should have given up retrying within 30 days; if it hasn't, manual reconciliation is correct.

**Alternative:** never clear. Storage cost is negligible. The reason for the sweep is hygiene, not performance. If the team prefers, leave the column populated forever.

## Lab charge timing — order vs result

**Choice:** when does the Lab module call `POST /charges` — at order placement, or at result finalisation?

**Recommendation (Phase 1):** at **order placement**. Reasoning:

- The patient is still at the counter when the order is placed; billing is collected at that point.
- Some tests have a per-collection-tube cost that is incurred whether or not the result is produced (a no-show is still billed for the sample collection).
- Cancellation between order and result is rare and is handled by the bill-amendment flow.

**Counter-argument (worth knowing):** for outpatient lab tests where results determine which add-on tests are ordered, charge-at-result avoids over-billing for tests not actually run. Production HIMS handles this via "lab packages" with one upfront charge per panel. Phase 2 (with packages) makes the upfront charge cover the panel; individual add-on tests outside the panel are charged separately at order time.

## Pharmacy charge timing — order vs dispense

**Choice:** when does the Pharmacy module call `POST /charges` — at prescription / order, or at dispense?

**Recommendation:** at **dispense**, not at prescription.

- Patient is charged for what was actually dispensed.
- Substitutions (generic vs brand, partial fills) are common; charging at prescription would require frequent amendment.
- Aligns with retail pharmacy practice.

Out-of-stock at dispense raises an alert to the counter; no charge is captured.

## Configurator-controlled vs hard-coded discount thresholds  [Phase 2 — NOT in Phase 1]

> **Not a Phase 1 concern.** Phase 1 has no approval workflow — the operator types in any discount percentage freely; only the bill-level `discount_amount` / `discount_percentage` / `discount_reason` fields are populated. The `discount_approvals` table and its threshold-routing logic land in Phase 2.

**Phase 2 choice:** the LLD says discount thresholds are Configurator-controlled. Initial Phase 2 implementation hard-codes them with a TODO; later wires them through Configurator.

**Recommendation:** ship Phase 2 with hard-coded thresholds (5%, 15%, 30%) and the approval-level mapping in code. Add `configurator.discount_approval_policies` in the Configurator's next revision, and wire billing to read from it via the Configurator's config API.

**Why defer further:** the Configurator has its own LLD and review cycle; adding a Phase 2 dependency on a new Configurator table risks scope creep. The hard-coded values are correct for the demo tenant.

## Where do "system" charges live?

**Choice:** non-clinical charges — registration fee, consumable charges added by counter operator without a clinical module source.

**Recommendation:** `bill_items.item_type = 'ADJUSTMENT'`, `source_module = 'manual'`, `source_ref = NULL`, `created_by` = operator. The `item_code` references the catalog (`service_master`) but the absence of a `source_module` clarifies that no clinical row originated this line.

Phase 1 supports registration fees added by frontdesk this way. Phase 2 may introduce a `frontdesk` module that emits its own charges; at that point, registration fees become `source_module='frontdesk'`.

## Transactionality boundary

**Choice:** what runs inside a single Postgres transaction.

**Guideline:**

- **One transaction per bill mutation.** `INSERT bill_items` + `UPDATE bills` totals run inside one transaction. Two bill_items added in two separate API calls are two transactions.
- **Payment + bill update** runs inside one transaction.
- **Advance utilisation + bill update** runs inside one transaction.
- **Discount approval + line/bill recomputation** runs inside one transaction.
- **Event publication** is *outside* the DB transaction. In Phase 1, the in-process bus dispatches synchronously *after* commit; if a consumer fails, the bill state is still correct. In Phase 2+ (durable bus), the outbox pattern ensures eventual delivery.

**What to avoid:**

- Spanning a transaction across HTTP calls to other modules (e.g., calling EMPI inside a bill transaction). The transaction stays local; the EMPI call is on the read path, not the write path.
- Holding a transaction open while waiting for a payment gateway callback. The `payments.status = 'PENDING_GATEWAY'` row commits in one transaction; the callback's update commits in another.
