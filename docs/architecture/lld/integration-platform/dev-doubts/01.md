# Integration Hub -- LLD-deferred implementation doubts

These are the implementation-stage choices the LLD intentionally does not lock in. The schema accommodates either path; pick during implementation.

---

### 1. Timer worker leader-election

The timer worker (`SELECT ... FOR UPDATE SKIP LOCKED` polling) must avoid duplicate firing across pods.

| Option | Pro | Con |
|---|---|---|
| `pg_advisory_lock` (recommended) | In-DB, zero new infra, well understood | Single PostgreSQL connection holds the lock |
| `LISTEN/NOTIFY` event-driven | Less polling | Requires pub/sub; loses messages if no listener |
| Kubernetes leader-election (k8s coordination.k8s.io API) | Standard, well-tooled | Couples Integration Hub to k8s |

**Recommendation:** `pg_advisory_lock`. The platform already uses PostgreSQL; the lock is cheap; failover means another pod picks up the lock on next poll. Falls back to `SKIP LOCKED` semantics if multiple pods race -- duplicate firing is bounded.

---

### 2. `payload_storage_ref` strategy for v1

Inbound and outbound message payloads must be stored. PostgreSQL row vs object storage.

**Recommendation:** Hybrid. Inline `payload` TEXT/JSONB column on the message-log row when payload size <100KB. Object-storage URL otherwise (Azure Blob / S3 with KMS encryption). The message-log row stays narrow either way; `payload_storage_ref` holds either an inline marker (`inline:`) or an object URL.

A small additional column `payload_inline TEXT NULL` on the message-log tables holds the inline bytes; `payload_storage_ref` then refers to either inline or remote storage. **Schema decision deferred** -- the schema-reference.json shows just `payload_storage_ref`; the `payload_inline` column will be added in implementation if the team prefers the hybrid over either extreme.

---

### 3. FSM engine packaging

Should the engine live inside `modules/integration-hub/` or as a separate package `@hims/ts-sdk-workflow`?

**Recommendation:** Separate package. Phase-1 reuse case is hypothetical, but the engine's API surface is small and well-defined; treating it as a package from day one prevents Integration-Hub-specific assumptions from leaking in. The package depends only on `@hims/ts-sdk-db` (for Drizzle infra) and PostgreSQL.

---

### 4. Per-tenant timer worker concurrency limits

A noisy tenant could starve the timer worker. Should the worker rate-limit per tenant?

**Recommendation:** v1 -- no limit, monitor. v1.1 -- if observed contention, add a per-tenant in-flight cap (token bucket per `iq_tenant_id`). Implement via a small `tenant_timer_inflight` counter in Redis or a process-local LRU.

---

### 5. Adapter dispatch — strategy pattern vs registry

How does inbound HTTP routing know which adapter to invoke for a given request?

**Recommendation:** Adapter-registry pattern. Adapters self-register at process startup with `{ kind: 'abdm', endpoints: [{path:'/v3/profile/on-share', handler}, ...] }`. The Inbound Gateway router builds a Fastify route table from the registry. New integrations are added by registering, not by editing router code.

---

### 6. Vault adapter abstraction

`integration_credentials.vault_ref` is opaque. How does the runtime resolve it?

**Recommendation:** Add `@hims/ts-sdk-secrets` package (deferred to its own LLD when first needed). For Phase 0 the resolver is a simple in-process map seeded from environment variables (developer-friendly), with the production wiring (Azure Key Vault SDK) added in Phase 1 alongside the ABDM adapter.

---

### 7. ABDM environment switching (sandbox <-> production)

A tenant runs `kind=abdm, environment=sandbox` for testing and `kind=abdm, environment=production` for live. The two sets of credentials, gateway URLs, and CM-IDs are in separate `integrations` rows.

**Recommendation:** v1 supports this via separate rows. The FSM workflow row references `integration_id`; switching environments is simply directing new workflows to the production integration row. In-flight workflows on the sandbox integration continue to completion.

---

### 8. ABHA address validation against gateway

The platform's local Zod validator checks format (`name@suffix`); the gateway alone authoritatively says whether `ayush@sbx` actually exists. Should the platform pre-check?

**Recommendation:** Check format locally (fast, no round-trip). Confirm existence only when the user takes a meaningful action (link to patient, request OTP). Avoid speculative existence-check round-trips on every keystroke.

---

### 9. M3 HIP bundle assembly fan-out

Per a granted consent, the HIP must serve bundles for *multiple* care contexts. Should the FSM iterate sequentially or fan out?

**Recommendation:** Sequential v1; small consent typically covers 1-5 contexts. Add fan-out when observed concurrency would benefit. The encryption step is bundle-by-bundle so parallelism is straightforward.

---

### 10. Audit retention

`integration_audit_log` will grow large. Retention policy?

**Recommendation:** 7 years (NABH minimum for clinical records). Partition by month. Move >90-day rows to a cold-storage table on the same shard (PostgreSQL inheritance) for cheaper read; full DELETE only after the 7-year horizon.

---

### 11. ABDM gateway TLS pinning

ABDM's gateway is at fixed hostnames. Pin TLS certificates for stronger security?

**Recommendation:** Don't pin in v1. ABDM rotates certificates periodically; pinning has caused outages in other integrators. Use the system trust store. Revisit if a security review requires it.

---

### 12. Single-pod vs split-pod deployment

[01-schema-design.md §7](../01-schema-design.md#7-service-deployment) says Phase 0/1 deploys a single pod-type running both Inbound and Outbound responsibilities; splitting comes later.

**Recommendation:** Hold this; split when *either* (a) inbound traffic from lab analyzers becomes noisy enough to noticeably affect outbound retries, or (b) a separate ops team wants to own one direction. Until then, one pod-type is simpler.
